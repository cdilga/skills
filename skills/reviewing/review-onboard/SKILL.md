# review-onboard — build persistent review context for a repo

Run once per repo (re-run anytime to refresh — it is idempotent and merges
into existing notes rather than overwriting hand-edits). Read-only on the repo
and on GitHub; writes only under `~/.reviews/` unless the human opts into the
repo-local skill at the end.

## Input

A repo (`owner/repo`, a GitHub URL, or the current directory's `origin`).

## Step 1 — Identity & access

```bash
gh auth status
gh api user --jq .login          # YOUR login — used for history mining below
gh api repos/<owner>/<repo> --jq '{permissions, default_branch, archived}'
```

Note your permission level (can you approve? request changes?) and whether
you appear in `CODEOWNERS` (check `.github/CODEOWNERS`, `CODEOWNERS`,
`docs/CODEOWNERS`) — record which paths are yours.

## Step 2 — Repo mechanics (what every review session needs on minute one)

From a local clone (clone to `~/.reviews/checkouts/<owner>/<repo>` if needed):

- **Instruction files**: `AGENTS.md` (root + nested), `CLAUDE.md`,
  `.github/copilot-instructions.md`, `.github/instructions/*`,
  `CONTRIBUTING.md` — summarize the rules a reviewer must hold authors to.
- **Build/test/lint**: derive the exact commands (from instructions first,
  else `package.json` scripts / `Makefile` / `Cargo.toml` / `pyproject.toml` /
  CI workflow files). RUN the test command once to learn its cost — record
  "fast (~30s)" vs "heavy (~10m, prefer targeted runs)".
- **Architecture sketch**: 5–15 lines — top-level layout, the 3–5 load-bearing
  modules, where the dragons are (the dirs with the most churn:
  `git log --since=6.months --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20`).
- **Adjacent tooling, only if real**: if the instructions mention an issue
  tracker or CI/CD system, check whether a matching CLI exists on this machine
  (`which …`). Record what exists and the invocation pattern the repo
  documents. If nothing exists, record "GitHub issues + `gh pr checks` only" —
  never invent tooling.

## Step 3 — Mine YOUR review history (the reviewer-voice load)

```bash
gh search prs --repo <owner>/<repo> --reviewed-by @me --state all --limit 50 \
  --json number,title,url
# then for a sample (10–20 PRs, most recent first):
gh api "repos/<owner>/<repo>/pulls/<N>/comments" --paginate --jq '.[] | select(.user.login=="<you>") | {path, body}'
gh api "repos/<owner>/<repo>/pulls/<N>/reviews" --paginate --jq '.[] | select(.user.login=="<you>") | {state, body}'
```

From the sample, distill into `reviewer-voice.md`:

- **Recurring themes** you flag (e.g. "always asks for rollback notes on
  migrations", "pushes back on broad try/except") — these become standing
  lenses for `review-kickoff`/`review-deeper` in this repo.
- **Severity habits** — what you actually block on vs let slide.
- **Phrasing** — 3–5 verbatim examples of how you write comments, so
  `review-walkthrough` drafts in your voice.
- **Verdict base rates** — roughly how often you approve vs request changes
  (keeps drafted verdicts calibrated to you).

If you have reviewed nothing here yet, mine the repo's culture instead: read
the review threads of the last 10 merged PRs — what do respected reviewers
flag, what gets a change request, what tone is normal. Record that as the
starting voice and mark it `inferred-from-repo, not yet personal`.

## Step 4 — Write the persistent store

```
~/.reviews/<owner>/<repo>/
  repo-notes.md        # Steps 1–2: access, commands, architecture, tooling, CODEOWNERS paths
  reviewer-voice.md    # Step 3
```

Both files start with a `<!-- generated by review-onboard on <date>; safe to
hand-edit, re-runs merge -->` header. On re-runs, update generated sections
in place and leave human-added sections alone.

## Step 5 — Optional: repo-local skill

If this repo has unusual mechanics (custom build farm, special test
entrypoints, a documented tracker CLI), offer to generate a small repo-local
skill — same pattern as a browser-harness-style project skill — at
`~/.agents/skills/<repo>-review-context/SKILL.md`, containing just the
mechanics (build/test/tooling invocations) so ANY future session in any
harness picks them up without reading the notes. Only create it if the human
says yes; show the content first.

## Report

Summarize: your access level, the test command + cost, the 3 most useful
things learned about the repo, the 3 strongest themes in your reviewer voice,
and confirm the notes paths. Close with: "ready — `review-kickoff <PR url>`
when the next Teams ping lands."
