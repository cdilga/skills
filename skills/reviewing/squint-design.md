# squint — design

**Status:** design, settled 2026-06-15. Supersedes `temporal-design.md` (the elaborate
scheduled-sweep model was rejected — see §9).

`squint` is a PR-review suite for a trusted human reviewer. Generic, tool-agnostic
skills that turn "someone pinged me to review their PR" into a deep, multi-round,
propose-only review where **you** stay the reviewer of record. Built to run under
Copilot CLI and OpenCode (and anything reading `~/.agents/skills`).

The whole arc of the design is **subtractive**: no durable findings ledger, no
per-repo bespoke skills maintained by a robot, no scheduled cron. State is either
disposable (per-PR) or a deliberately-authored, human-maintained artifact.

---

## 1. Skill roster

| Skill | Role |
|---|---|
| `squint-kickoff` | First deep round on a PR URL: boot context, worktree checkout, subagents, findings |
| `squint-deeper` | Another finding-hunt round; new lens (incl. a verification lens); loop until dry |
| `squint-walkthrough` | Step through findings, render draft, post once. **The only skill that posts.** |
| `squint-cloud` | Cloud lane: set up / run / harvest reviews on remote Copilot agents |
| `squint-onboard` | Heavy, manual, two-kinds-of-output onboarding (see §5) |

Team-scoped specializations generated by onboarding: `acme-squint-*` (thin shims)
and `acme-ctx*` (context data). See §3.

## 2. The review loop runs on generics — onboarding is optional

```
squint-kickoff <url>   # read AGENTS.md/docs if present, else generics → worktree
                       #   checkout → subagents → round 1 → findings (worktree scratch)
squint-deeper [steer]  # more rounds, new lenses, until dry
squint-walkthrough     # step through findings → maybe post once via gh
```

Haven't onboarded? You get generics — the loop still works cold. Onboarding only
makes it richer and cheaper; it is never a precondition.

**Per-PR findings are disposable.** They live as scratch in the worktree, not in a
durable ledger. Once `squint-walkthrough` posts, **GitHub is the record**; tear the
worktree down and nothing accumulates. This is why there's no per-PR lifecycle to
manage. Reviewer voice is mined from posted GitHub reviews, not from local scratch,
so dropping the durable ledger costs nothing.

**GitHub-mutation boundary:** during *analysis*, every skill is read-only on the repo
and makes no GitHub mutations (its only writes are under `~/.squint/`). There are
exactly two deliberate, human-shown exceptions: `squint-walkthrough` posts the final
verdict (the only review-post — after the draft is shown, you approve, as one batched
review), and `squint-cloud` issues explicit, shown-before-run cloud-orchestration
requests (request a Copilot review / comment to invoke a cloud agent). Nothing else
mutates GitHub. If the PR head moved since the findings were written, posting is
refused until a `squint-deeper` reconciliation round re-anchors.

## 3. Naming & branding

`squint` is deliberately disjoint from Roger / `rr` (a separate, CLI-coupled
namespace). Being a unique prefix, squint skills never hit the hub's collision path.

| Tier | Pattern | Example |
|---|---|---|
| Generic procedure (installed once, shared) | `squint-<verb>` | `squint-kickoff` |
| Team flow (onboarded, thin shims) | `<team>-squint-<verb>` | `acme-squint-kickoff` |
| Team-shared context | `<team>-ctx` | `acme-ctx` |
| Project context | `<team>-ctx-<project>` | `acme-ctx-joinform`, `acme-ctx-app` |

- **Hub is organized team-first** (`acme-*` clusters all of a team's skills). Generics
  (`squint-*`) live in their own cluster — the seam between "the tool" and "a team's
  tailoring of it."
- **The prefix stops at team, not project.** `acme-squint-kickoff <url>` resolves the
  project at runtime from the PR's repo/path against each context skill's `repos:` /
  `paths:` frontmatter. So join-form vs full-app — whether two repos or one monorepo
  split by path — is handled by context resolution, not by more name segments.
- **Team flow skills are thin shims, not forks.** Each `acme-squint-<verb>` ≈ "load
  `acme-ctx` (+ resolved project ctx), then run the generic `squint-<verb>` procedure
  with these team overrides." The procedure lives once in the generic skill; team
  skills only bind context + tweaks. No procedure duplication.
- **Shared knowledge lives once.** Team-wide facts go in `acme-ctx`; project skills open
  with "load `acme-ctx` first," referencing not copying.

## 4. The review lenses (verification folded in)

`squint-deeper` rotates lenses across rounds: concurrency, security, API contracts,
tests/omissions, failure modes, performance, and a **verification lens** (parameter
tables, properties, fuzzing, metamorphic/differential checks, fault injection). There
is no separate verification skill — it's a lens.

## 5. `squint-onboard` — one skill, two kinds of output

Heavyweight, manual, run when *you* decide. The expensive part — deep mining of source
history, work history, design docs, prior agent sessions, architecture — is **shared**.
Only what gets written at the end differs:

- **Repo-readiness output:** author/improve `AGENTS.md` + the cross-tool `.agents/skills/`
  scaffold + pointer files (§6, §7). Generic; helps every agent in the repo.
- **Review-tailoring output:** generate `acme-squint-*` shims + `acme-ctx*` context.

**Mode is the loading agent's judgment, not a hardcoded flag.** The skill describes both
kinds of output and instructs the agent to infer intent from the request and context,
**with a strong bias toward doing both** (the deep pass is already paid for, so the
marginal cost of the second output is small). It asks only when intent is genuinely
unclear *and* the difference matters.

**Mining is tool-agnostic.** The skill calls a *capability* — "search prior agent/session
history for what was tried, broken, or decided in these files" — never a specific tool.
Tools are named only as non-binding examples ("e.g. a session-history search like `cass`,
your harness's transcript search, or grepping local agent logs") and every step degrades
gracefully when none is present. No architecture lock-in.

**Decomposition, not prescription.** When authoring repo docs, push depth into a series of
focused `docs/` files referenced by path; keep `AGENTS.md` lean (§7). Propose, don't
impose — the human approves.

## 6. Cross-tool in-repo layout (Copilot CLI + OpenCode, incl. CI)

As of 2025-12-18 Copilot supports SKILL.md; both Copilot CLI and OpenCode natively read
root `AGENTS.md` and both scan `.agents/skills/` (and `.claude/skills/`). So checked-in
review skills + repo docs need **one layout, near-zero duplication**:

```
repo/
├── AGENTS.md                       # BOTH tools read natively (CLI + CI). The keystone.
├── .agents/skills/                 # BOTH tools scan for checked-in skills
│   ├── acme-squint-kickoff/SKILL.md
│   ├── acme-ctx/SKILL.md
│   └── acme-ctx-joinform/SKILL.md
└── .github/copilot-instructions.md # OPTIONAL, Copilot-only — keep a 1-line "See AGENTS.md."
```

Gotchas onboarding must respect:
- **SKILL.md frontmatter** `name` + `description` is identical across both tools (`name` =
  lowercase-hyphen = dir name) → skills author once, portable.
- **Nested `AGENTS.md` isn't reliably portable** across surfaces → keep critical rules in
  **root** `AGENTS.md`.
- **`CLAUDE.md` trap:** OpenCode ignores `CLAUDE.md` when `AGENTS.md` exists; Copilot
  merges it → one source of truth; symlink `CLAUDE.md → AGENTS.md` or omit.
- **`.github/copilot-instructions.md`** is only for Copilot surfaces that don't honor
  AGENTS.md (github.com Chat / code review). Keep it a thin pointer, not a duplicate body.

## 7. AGENTS.md craft (distilled from Dicklesworthstone's real files)

Token-efficiency thesis, in his framing: **`AGENTS.md` loads every turn, so it holds only
behavior-changing guardrails — depth gets pushed into on-demand skills and cited docs.**
His 800–1100-line files are the exception (they inline a whole ops manual); his own spec
calls for "short, skimmable" and his 178-line `franken_engine` is the model.

Portable principles `squint-onboard` (docs output) should apply:
1. **RULE 0 first: the user overrides this document.**
2. **Safety/irreversibility rules before architecture** (no-delete; no `rm -rf` / `reset
   --hard` without same-message auth) — they must survive skimming.
3. **Prohibitions as unhedged CAPS imperatives**, each with a one-line **why**.
4. **Build/test/lint as a copy-paste block** under a "(CRITICAL)" heading.
5. **No file proliferation / no `_v2` / no compat shims** inline — shapes every edit.
6. **Architecture as a terse Quick Reference**, depth cited to `docs/…`.
7. **Per-tool mini-template** (purpose · 3–6 commands · 1–3 gotchas · single entry-point).
8. **"Landing the Plane" completion checklist** at the end.
9. **Solve compaction with a re-read hook, not repetition.**
10. **Thin `CLAUDE.md` that delegates** to AGENTS.md + the top rules.

Skeleton:
```
# AGENTS.md — <project>   > one line: what it is + who this doc is for
## RULE 0 — User overrides this document
## Hard Safety Rules            (no-delete; irreversible-git; each rule + 1 "why")
## Toolchain & Commands         (build/lint/test, copy-paste, "CRITICAL")
## Code Editing Discipline      (edit-in-place; no _v2; no compat shims)
## Architecture — Quick Reference   (terse; deep detail → cite docs/ path)
## Project-Specific Non-Negotiables (3–6 repo-unique constraints)
## Landing the Plane            (session-completion checklist)
```

**Don't cargo-cult his idiosyncrasies:** "main only, no branches/worktrees ever" (specific
to his swarm-on-one-repo model — most teams want branches/PRs), and his large tool-appendix
documenting *his* toolchain (`br`/`bv`/UBS/`ntm`/Agent Mail). Replace with the repo's own.

## 8. Committed vs symlinked, and the per-project link manifest

Only **shared, lives-once, needed-in-many-places** artifacts are symlinked. Project-unique
artifacts are real committed files.

| Artifact | In a project repo | Symlink? |
|---|---|---|
| `acme-squint-*` shims | real committed files (must travel to CI/teammates) | No |
| `acme-ctx-<project>` (project context) | real committed file | No |
| `acme-ctx` (team-shared, used by many repos) | lives once canonically, needed in N repos | **Yes** |
| generic `squint-*` (local convenience) | already global via `~/.agents/skills` | Optional |

Onboarding handling, kept simple:
1. **Per-project link manifest** — a *committed* file at repo root `.agents/squint-links.md`,
   one entry per symlink: `target → source`, purpose, local-only flag. The symlinks
   themselves stay gitignored (they don't resolve elsewhere); the manifest documenting
   them is committed so CI and teammates know which local links to recreate.
2. **Idempotent re-link step** — re-running onboarding re-asserts links using the same
   collision logic as `install.sh` (quiet if already correct, warn on foreign clobber,
   skip real dirs). A per-project mini-installer.
3. **Gitignored, not committed** — a symlink to `~/.agents/skills/...` won't resolve
   elsewhere, so these go in `.gitignore` / `.git/info/exclude`.

**CI caveat the notes must state:** symlinks don't travel to CI or teammates. For shared
team context, the notes record the fallback — either CI runs an install step (or clones a
team-skills repo), or that one shared file is committed as a real copy into each repo and
re-synced on re-onboard. Symlink = zero drift but local-only; committed copy = travels but
you re-sync it. Onboarding documents which choice each project made.

## 9. Temporal: the human is the scheduler

**No cron, no sweep, no queue.** Rejected the elaborate scheduled-maintenance design because
the artifacts that would need maintaining were removed:
- Per-PR state is disposable (worktree); GitHub is the record. Nothing to age out.
- Repo facts live in `AGENTS.md` / `acme-ctx*`, maintained like any code — git-versioned,
  PR-reviewed. You don't run a cron over your repo's docs.
- Staleness is checked **at the moment of use** — `squint-kickoff` can notice "this context
  is N commits old, want a refresh?" — which is better-timed than a timer firing on repos
  you may not touch that week.

You re-run `squint-onboard` by hand when you judge a repo has drifted. Revisit automation
only if this manual model actually hurts.

## 10. Installer

Grouped-skill discovery (`skills/<group>/<name>/SKILL.md` → hub symlink by basename). The
hub install now reads the existing symlink and **attributes collisions to the real owning
collection** (no guessing), staying quiet when the link is already ours. Branding the suite
`squint-*` means review skills never collide in the first place.

## 11. Open / deferred

- `acme-ctx` shared-context distribution for CI (install step vs committed copy) — per-project
  choice, documented at onboard time; no global mechanism yet.
- Multi-machine `~/.agents/skills` divergence — out of scope unless it bites.
- Exact headless invocation strings per harness for the cloud lane — pin when building
  `squint-cloud`.
